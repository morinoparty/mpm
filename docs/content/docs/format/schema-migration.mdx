import { Callout } from "fumadocs-ui/components/callout";

mpmが読み書きする設定ファイルには、`schemaVersion` というファイル形式の版数が記録されています。
mpmはサーバー起動時にこの値を確認し、古い形式のファイルを現行の形式へ自動的に移行します。

## 📐 schemaVersion とは

`schemaVersion` は「mpmが定めるファイル構造の版数」です。
mpmのバージョンが上がって設定ファイルの構造が変わったとき、既存のファイルを壊さずに
新しい構造へ移行するための目印として使われます。

**現在の版数は `2` です。**

| ファイル | 記述場所 |
|---------|---------|
| [`mpm.json`](/docs/format/mpm-config) | トップレベルの `schemaVersion` |
| [`config.json`](/docs/format/config) | トップレベルの `schemaVersion` |
| [`metadata/*.yaml`](/docs/format/managed) | トップレベルの `schemaVersion` |

<Callout type="info" title="mpm-lock.yaml は対象外">
[`mpm-lock.yaml`](/docs/format/mpm-lock) は `mpm.json` とメタデータから
いつでも再生成できるファイルのため、`schemaVersion` を持たず、自動移行の対象にもなりません。
</Callout>

<Callout type="warn" title="mpm.json の version とは別物です">
`mpm.json` には `version`（あなたのプロジェクトのバージョン）というフィールドもありますが、
`schemaVersion` とはまったく役割が異なります。
`version` は利用者が自由に付ける値で、`schemaVersion` はmpmが管理する値です。
</Callout>

## 🔄 起動時の自動移行

mpmはサーバー起動時、他の処理が設定ファイルを読み込むよりも **前** に、
上記3種類のファイルを走査して版数を確認します。

| ファイルの `schemaVersion` | mpmの動作 |
|--------------------------|----------|
| 記載なし | 旧形式（v1）とみなして、現行の形式へ移行します |
| `1` | 現行の形式へ移行します |
| `2`（現行） | **何もしません**。ファイルへの書き込みも行いません |
| `3` 以降 | 移行せず、警告のみを出力してそのまま扱います |

移行は「版数を1つずつ上げる」仕組みになっているため、
将来v3・v4が登場した場合も、v1のファイルはv1→v2→v3…と順番に変換されて現行版へたどり着きます。

<Callout type="info" title="手で書き換える必要はありません">
mpmが設定ファイルを保存するたびに、現行の `schemaVersion` が自動的に記録されます。
利用者がこの値を手で書き換える必要はありません。
</Callout>

### 移行結果のログ

移行が行われた場合、サーバーコンソールに次のようなログが出力されます。

```log
[mpm] Migrated 2 file(s) to schema v2.
```

移行できなかったファイルがある場合は、ファイルごとに警告が出力されます。

```log
[mpm] metadata/LuckPerms.yaml のスキーマ移行に失敗しました: ...
```

## 🛡️ 安全性について

自動移行は、既存のデータを壊さないことを最優先に設計されています。

### 現行版数のファイルには触れません

`schemaVersion` が既に `2` のファイルは読み取るだけで、書き込みは一切行いません。
そのため、mpmを何度再起動しても、移行済みのファイルの内容やタイムスタンプは変化しません（冪等）。

### より新しい版数のファイルはダウングレードしません

新しいバージョンのmpmで書き込んだファイルを、古いバージョンのmpmで読み込んだ場合、
mpmは移行を行わずに警告だけを出力し、ファイルをそのまま扱います。

```log
[mpm] config.json は新しいスキーマ (v3) で書かれています。ダウングレードは行わず、そのまま扱います。
```

さらに、起動時の移行だけでなく **通常の保存処理でも** 同じ判定を行います。
保存しようとしたファイルが現行版数より新しい場合、mpmは書き込みを中止して警告を出力し、
その操作自体も失敗として扱います。

```log
[mpm] mpm.jsonの保存を中止しました: mpm.json は、このmpmが対応するスキーマ版数(v2)より新しいv3で書かれています。
```

これは、移行処理が触らなかったファイルを保存処理が現行版数へ書き戻してしまい、
未知の設定項目が失われることを防ぐための仕組みです。

書き込みの中止は、それを引き起こしたコマンドにもそのまま伝わります。
たとえば `/mpm pin` や `/mpm uninstall` は成功と表示されずに中止の理由をそのまま返すため、
「コマンドは成功したように見えるのに、ファイルの内容が変わっていない」という状態にはなりません。

### 中断はファイルを書き換える前に行われます

版数の判定は、書き込みの直前だけでなく **操作の開始前** にも行われます。
JARファイルの差し替えや削除といった後戻りできない処理に入る前に確認するため、
「更新は失敗したのにJARだけ新しくなっている」「アンインストールは失敗したのにJARだけ消えている」
といった中途半端な状態は発生しません。

```
CarbonChat.yaml は、このmpmが対応するスキーマ版数(v2)より新しいv3で書かれています。
```

中止の理由は、そのままコマンドの結果として返されます。
この事前確認はファイルを読むだけで、内容には一切手を触れません。
書き込み直前の判定もそのまま残してあるため、二重に保護されています。

<Callout type="warn" title="バージョンを戻す場合">
古いmpmには未知の設定項目を解釈する手段がありません。
そのため、書き込みは中止されて設定が保持される代わりに、
プラグインの追加・更新などファイルの保存をともなう操作はエラーとなります。
mpmのバージョンを戻す場合は、事前に `plugins/mpm/` ディレクトリのバックアップを取り、
該当ファイルを退避するかmpmを最新版へ戻してください。
</Callout>

### 1件の失敗が全体を止めません

あるファイルの移行に失敗しても、他のファイルの移行処理やサーバーの起動は継続されます。
失敗したファイルは変更されずにそのまま残り、警告ログにファイル名と理由が出力されます。

移行のあとに続く `config.json` の読み込みについても同様です。
ファイルが壊れている場合はもちろん、読み取り権限が無いなどの理由で読み込めない場合も、
mpmはデフォルト設定で起動を続行します。
このとき対象のファイルには一切手を触れないため、原因を取り除いて
`/mpm reload` を実行すれば元の設定がそのまま読み込まれます。

```log
[mpm] config.jsonの読み込みに失敗したため、デフォルト設定で起動します（ファイルは変更していません。内容を確認して修正してください）: plugins/mpm/config.json - ...
```

### 書き換えられないファイルは移行しません

移行後のファイルは、一時ファイルへ書き出してから元のファイルへ **原子的に** 置き換えます。
何らかの理由でこの置き換えができない場合、mpmは元のファイルに一切手を触れず、
そのファイルの移行だけを失敗として扱います。
中途半端に書き換えられたファイルが残ることはありません。

### 未知の項目は保持されます

`mpm.json` と `config.json` の移行では、mpmが知らない項目もそのまま引き継がれます。
手動で追加した項目が、移行によって消えることはありません。

なお `mpm.json` と `config.json` は厳密なJSONとして読み込むため、`//` や `/* */` といった
コメントを書き込むことはできません。コメントを含むファイルは移行も読み込みも行えず、
移行はそのファイルだけを失敗として扱い（ファイルは変更されません）、
`config.json` の場合はデフォルト設定で起動します。
ドキュメント中のサンプルに付いているコメントは説明のためのものです。

## 📋 版数ごとの変更点

### v1 → v2

| ファイル | 変更内容 |
|---------|---------|
| `mpm.json` | `schemaVersion: 2` を追加します（構造の変更はありません） |
| `config.json` | `schemaVersion: 2` を追加し、廃止された `settings.schedule.dryRun` を削除します |
| `metadata/*.yaml` | `schemaVersion: 2` を追加します（構造の変更はありません） |

<Callout type="info" title="schedule.dryRun の廃止について">
`settings.schedule.dryRun` は、スケジュール自動更新を「チェックのみ」で動かすための設定でした。
現在は [自動更新の対象がバージョン指定によって決まる](/docs/usage/update) ようになったため、この設定は廃止されました。

なお、`/mpm update --dry-run` などのコマンドの `--dry-run` オプションは今までどおり利用できます。
</Callout>
